# Audit, 2026-07-25: UNSOUND

VDS was committed at `b533a67` with a message claiming it applied the [2026] VJS-CC-OPBOX 3
D2/D3 ratio "from the first commit". **That claim is false and is withdrawn.** An adversarial
agent, briefed to refute rather than review, found seven defects with reproducible exit codes
within an hour of the commit landing.

This file exists because the commit message is immutable and wrong. Anyone reading that message
needs to find this.

## What was claimed, and what was true

| Claimed | Actual |
|---|---|
| "a hand-written proof record is void, and the schema enforces this by fixing `capture_mode` to the single value `automatic`" | Fixing an enum to one value makes forgery **trivial**, not impossible. A hand-written proof for a script that does not exist was accepted as warrant evidence, exit 0. |
| S-6(2): the warrant ordering "is the entire mechanism" | No ordering check existed. W3 was recorded as granted with W1 and W2 not granted. |
| S-2(7): a pin "carries source_value_digest and target_value_digest ... and never the two strings. This is what keeps the pin a gate rather than a store." | Unsalted sha256 over a 24-bit domain is not one-way in any practical sense. **All 52 values recovered in 27 seconds on one CPU.** `.vds/` therefore stored 26 decided and 26 shipped colours, which is precisely the storing form CC-OPBOX 3 forbids. |
| S-4(2): ledgers are "generated inventories, never hand-edited", and freshness is checked before every read | The freshness digest covered the source files, not the ledger's own derived rows. Hand-deleting one row turned the anti-drift proof from FAIL to PASS **and minted a proof record attesting to the pass.** |
| S-7(2): a proof is valid only if a named test seeds a violation and asserts the non-zero exit, and "the enforcement lock entry cannot be written without naming that test, which is how the condition is enforced rather than requested" | `tools/tests/` was **empty**. By VDS's own statute none of the three implemented proofs was a proof, and none could lawfully be named as evidence. The runner wrote them as `status: passed` regardless. |
| S-8(1): the enforcement lock trips "a loud, blocking finding" on a weakening edit | `lock verify` never opened the invoker it named. A lock declaring a CI workflow that does not exist verified clean, exit 0. The named failing-direction test was checked at `lock add` and never at `verify`, so deleting it afterwards still verified clean. |
| VDS is an enforcement surface over the Opbox frontend | Nothing in that repository invoked any VDS proof. |

## The pattern, which matters more than any single defect

Every one of these is the same failure: **a mechanism was described in the specification and the
description was mistaken for the mechanism.** The author wrote "the schema enforces this" and did
not check that the schema enforced it. Wrote "the ordering is the entire mechanism" and did not
implement the ordering. Wrote that a pin holds no values and did not test whether the values were
recoverable.

This is exactly the defect CC-OPBOX 3 found in the Opbox token gate, reproduced inside the tool
built to prevent it, roughly ninety minutes after reading the ruling. That is not ironic so much
as instructive: **the failure mode is the default.** Writing the gate feels like catching the
defect, and it is not.

The corollary for anyone using VDS: do not trust a clause in `VDS.md` because it is written
confidently. Test the claim. Both of the two most serious findings here were found by testing a
claim rather than reading it, and both claims read as settled fact.

## Standing

Recorded before the fixes, deliberately. A repository whose history shows only the clean state
teaches nothing, and the audit is more valuable than the code it audits.

The remediation is tracked separately. Each defect is closed only when the auditor's own attack
has been re-run and observed to fail, and any that cannot be fully closed is recorded here with
what remains open rather than quietly dropped.
